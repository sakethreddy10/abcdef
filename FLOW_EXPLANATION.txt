RAG PROJECT QUERY FLOW EXPLANATION
==================================

This document explains what happens from the moment a user submits a question
until the API returns the final answer.

Example request:

    POST /query

    {
      "question": "Explain swarm management",
      "bucket": "bucket_1",
      "top_k": 3
    }


1. APPLICATION STARTUP
======================

The application starts in app/main.py. It imports the router from
app/api/routes.py and registers the API endpoints with FastAPI.

When routes.py is imported, shared service objects are initialized:

    EmbeddingService
    VectorStoreService
    RetrievalService
    LLMService
    RAGService

The current models are:

    Embedding model: BAAI/bge-base-en-v1.5
    Answer model: qwen2.5:7b

The embedding model converts text into vectors. Qwen generates the final answer.


2. REQUEST VALIDATION
=====================

The request reaches query_rag() in app/api/routes.py.

FastAPI validates the JSON body using QueryRequest from
app/models/schemas.py.

The request contains:

    question:
        The user's natural-language question.
    bucket:
        Optional bucket_1 or bucket_2 filter. If omitted, all buckets are used.
    top_k:
        Number of final context chunks. It must be between 1 and 20.

Invalid request data returns HTTP 422.


3. CHECK THE VECTOR STORE
=========================

The route calls vector_store.count(). This function is in
app/services/vector_store_service.py and returns the number of chunks stored in
ChromaDB.

If the count is zero, the API returns HTTP 400 and asks the user to run /ingest
first. No question can be answered until documents have been indexed.


4. START THE RAG PIPELINE
=========================

The route calls:

    rag_service.query(
        question=payload.question,
        bucket=payload.bucket,
        top_k=payload.top_k,
    )

This enters query() in app/services/rag_service.py. RAGService coordinates
retrieval, prompt construction, answer generation, and source citations.


5. EMBED THE QUESTION
=====================

RAGService calls retriever.retrieve() from
app/services/retrieval_service.py.

RetrievalService calls:

    self._embedder.embed_one(question)

This enters app/services/embedding_service.py. EmbeddingService uses
BAAI/bge-base-en-v1.5 through SentenceTransformers.

The question becomes one 768-dimensional floating-point vector. For example:

    [0.012, -0.041, 0.087, ...]

The vector represents the meaning of the question. Document chunks were
embedded with the same model during ingestion, so the vectors can be compared.


6. SEARCH CHROMADB
==================

RetrievalService passes the question vector to:

    vector_store.search(
        query_embedding=query_vector,
        top_k=max(top_k * 2, top_k),
        bucket=bucket,
    )

If top_k is 3, the initial search asks ChromaDB for 6 candidates. Extra
candidates are retrieved so the application can improve their order before
selecting the final 3.

VectorStoreService searches the persistent ChromaDB collection named
rag_documents in the vectorstore directory.

ChromaDB uses cosine distance to compare the question vector with stored chunk
vectors. A lower distance means the chunk is more similar to the question.

If bucket_1 was supplied, the search uses this metadata filter:

    {"bucket": "bucket_1"}

Without a bucket, chunks from both buckets may be searched.

Each result contains:

    text:
        The original chunk text.
    metadata:
        Source filename, page, file type, bucket, and chunk index.
    distance:
        Cosine distance from the question vector.

Results above RETRIEVAL_MAX_DISTANCE are removed. The current default is 0.72.

The remaining results are returned as dictionaries such as:

    {
      "text": "Swarm management requires...",
      "source": "28_urban_beekeeping_basics.pdf",
      "page": "2",
      "file_type": ".pdf",
      "bucket": "bucket_1",
      "chunk_index": 1,
      "distance": 0.21
    }


7. CROSS-ENCODER RERANKING
==========================

RetrievalService sends each vector-search candidate and the question to the
local CrossEncoder model:

    cross-encoder/ms-marco-MiniLM-L-2-v2

The model scores the question and chunk together, then the highest-scoring
chunks are returned. With the default top_k of 5, ChromaDB supplies 10
candidates and the reranker returns the best 5. The reranker loads lazily on
the first query and is reused for later queries.

If no chunks remain, RAGService returns a no-relevant-documents message and does
not call Qwen.


8. BUILD THE CONTEXT PROMPT
===========================

When relevant chunks exist, RAGService calls build_prompt() in
app/services/rag_service.py.

It places the retrieved text and metadata into a prompt like this:

    --- START OF CONTEXT ---
    [Source: 28_urban_beekeeping_basics.pdf | Page: 2 | Bucket: bucket_1]
    Swarm management requires consistency over time...
    --- END OF CONTEXT ---

    Question: Explain swarm management

    Answer:

The source and page information lets the model produce useful citations.


9. SEND THE PROMPT TO QWEN
==========================

RAGService calls LLMService.generate() in app/services/llm_service.py.

Two messages are sent to Ollama:

    System message:
        Instructions to use only the retrieved context, avoid guessing, answer
        directly, and cite source names and pages.
    User message:
        The context prompt containing retrieved chunks and the question.

LLMService calls the local Ollama server with:

    model: qwen2.5:7b
    temperature: 0.2
    maximum output: configured OLLAMA_MAX_TOKENS value

Ollama returns a response containing generated message content. LLMService
extracts response["message"]["content"] and returns it as a trimmed string.

If Ollama is unavailable, the API returns HTTP 503. If the configured model is
missing, the error explains that the model must be pulled first.


10. CREATE SOURCE CITATIONS
===========================

After the answer is generated, RAGService reads source information from the
retrieved chunks.

It removes duplicate source/page/bucket combinations and creates citations
containing:

    document
    page
    bucket
    file_type

The internal result contains the question, answer, bucket, source list, and
retrieved chunks.


11. FORMAT THE API RESPONSE
===========================

Back in query_rag() in routes.py, each source is converted into a SourceCitation
object. The complete result is validated using QueryResponse from schemas.py.

The final JSON response contains:

    {
      "question": "Explain swarm management",
      "answer": "Swarm management requires consistent monitoring...",
      "bucket": "bucket_1",
      "sources": [
        {
          "document": "28_urban_beekeeping_basics.pdf",
          "page": "2",
          "bucket": "bucket_1",
          "file_type": ".pdf"
        }
      ]
    }

The retrieved_chunks field is used internally but is not included in the final
QueryResponse sent by this route.


12. DISPLAY IN THE BROWSER
==========================

The frontend in app/static/index.html sends the POST /query request. When the
JSON response arrives, JavaScript displays data.answer in the answer area and
uses data.sources to populate the Sources section.

The frontend does not generate the answer. It only displays the answer produced
by Qwen and the citations returned by the API.


COMPLETE FLOW
=============

    User question
        -> POST /query
        -> QueryRequest validation
        -> Check ChromaDB is not empty
        -> RAGService.query()
        -> Embed question with BAAI/bge-base-en-v1.5
        -> Search ChromaDB using cosine distance
        -> Filter by bucket and distance threshold
        -> CrossEncoder reranking
        -> Select final top-k chunks
        -> Build context prompt
        -> Send prompt to qwen2.5:7b through Ollama
        -> Generate grounded answer
        -> Create source citations
        -> Validate QueryResponse
        -> Return JSON
        -> Display answer in browser


ROLE OF EACH MAIN FILE
======================

    app/main.py
        Creates the FastAPI application and registers routes.

    app/api/routes.py
        Receives HTTP requests and returns HTTP responses.

    app/models/schemas.py
        Validates request and response data with Pydantic.

    app/services/rag_service.py
        Orchestrates the complete RAG question-answering flow.

    app/services/retrieval_service.py
        Embeds questions, searches the vector store, and reranks results.

    app/services/embedding_service.py
        Converts text into embedding vectors.

    app/services/vector_store_service.py
        Stores and searches vectors, text, and metadata in ChromaDB.

    app/services/llm_service.py
        Sends grounded prompts to Qwen through Ollama.

    app/static/index.html
        Sends browser requests and displays the returned answer and sources.
