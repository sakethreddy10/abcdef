RAG PROJECT API EXPLANATION
===========================

This file explains the FastAPI endpoints implemented in app/api/routes.py.
The API runs through app.main and is normally available at:

    http://127.0.0.1:8000

Interactive API documentation is available at:

    http://127.0.0.1:8000/docs

The API uses two document buckets:

    bucket_1
    bucket_2

A bucket is a logical group of documents. Querying a specific bucket prevents
results from the other bucket from being used.


1. GET /
=========

Purpose:
    Serves the browser user interface for the RAG application.

Response:
    The app/static/index.html web page.

Example:

    GET http://127.0.0.1:8000/

This endpoint does not run a RAG query. It only loads the frontend.


2. GET /health
==============

Purpose:
    Checks whether the application and its main services are available.

What it checks:
    - Whether Ollama can be reached.
    - Which Ollama model is configured.
    - How many chunks are stored in ChromaDB.
    - Which embedding model is configured.

Example request:

    GET http://127.0.0.1:8000/health

Example response:

    {
      "status": "healthy",
      "ollama_connected": true,
      "ollama_model": "qwen2.5:7b",
      "vector_store_chunks": 120,
    "embedding_model": "BAAI/bge-base-en-v1.5"
    }

Status values:
    healthy:
        Ollama is reachable.
    degraded:
        Ollama is not reachable, although the application can still report
        vector-store information.


3. GET /documents
=================

Purpose:
    Returns statistics about the ChromaDB vector store.

Example request:

    GET http://127.0.0.1:8000/documents

Example response:

    {
      "total_chunks": 120,
      "collection_name": "rag_documents",
    "embedding_dimension": 768
    }

Field meanings:
    total_chunks:
        Number of document chunks currently stored.
    collection_name:
        ChromaDB collection used by the application.
    embedding_dimension:
        Number of values in each embedding vector. The current
        BAAI/bge-base-en-v1.5 produces 768-dimensional vectors.


4. POST /ingest
===============

Purpose:
    Reads all supported documents from a bucket directory, extracts their
    text, splits the text into chunks, creates embeddings, and stores the
    chunks in ChromaDB.

Supported file types:
    - PDF
    - DOCX
    - TXT
    - CSV
    - XLSX
    - XLS
    - PNG
    - JPG
    - JPEG

Request body:

    {
      "bucket": "bucket_1",
      "directory_path": null
    }

Fields:
    bucket:
        Required bucket name. It must be bucket_1 or bucket_2.
    directory_path:
        Optional directory path. If omitted, the configured default directory
        for the selected bucket is used.

Example using the default directory:

    POST http://127.0.0.1:8000/ingest

    {
      "bucket": "bucket_1"
    }

Processing steps:
    1. Select the bucket directory.
    2. Compare each supported file's SHA-256 fingerprint with its indexed fingerprint.
    3. Parse only new or changed files.
    4. Delete chunks for changed files and files removed from the directory.
        5. Split parsed text into configured overlapping chunks.
    6. Create one embedding vector per new or changed chunk.
    7. Store text, vectors, metadata, and the document fingerprint in ChromaDB.

Unchanged files remain untouched. Changed files replace their old chunks, and
files no longer present in the directory are removed from that bucket.

Example response:

    {
      "status": "success",
      "bucket": "bucket_1",
      "documents_parsed": 12,
      "chunks_stored": 120,
      "message": "Successfully ingested 12 document item(s) producing 120 chunk(s) into bucket_1."
    }

Possible errors:
    400:
        Invalid bucket name.
    404:
        The selected directory does not exist.
    500:
        A parsing, embedding, or storage error occurred.


5. POST /upload/{bucket}
========================

Purpose:
    Uploads one or more supported files into a bucket and indexes them.

URL examples:

    POST http://127.0.0.1:8000/upload/bucket_1
    POST http://127.0.0.1:8000/upload/bucket_2

Request format:
    multipart/form-data
    Field name: files

The endpoint:
    1. Validates the bucket.
    2. Validates each filename, extension, and reported MIME type.
    3. Saves the uploaded files in the bucket directory.
    4. Parses the uploaded files.
    5. Chunks and embeds their extracted text.
    6. Deletes old chunks for those source filenames.
    7. Stores the new chunks in ChromaDB.

Unlike /ingest, this endpoint replaces only the uploaded source files. It does
not delete the other files already indexed in the bucket.

Example with PowerShell:

    curl.exe -X POST "http://127.0.0.1:8000/upload/bucket_1" `
      -F "files=@C:\path\to\document.pdf"

Example response:

    {
      "status": "success",
      "bucket": "bucket_1",
      "documents_parsed": 3,
      "chunks_stored": 18,
      "message": "Uploaded and indexed document.pdf (18 chunk(s))."
    }

Possible errors:
    400:
        Invalid bucket, missing filename, unsupported file type, or an obvious
        filename/MIME type mismatch.
    500:
        An upload, parsing, embedding, or storage error occurred.


6. GET /documents/sources
=========================

Purpose:
    Lists the unique source files currently represented in ChromaDB.

Example request:

    GET http://127.0.0.1:8000/documents/sources

Example response:

    {
      "sources": [
        {
          "document": "customer_feedback.csv",
          "bucket": "bucket_1",
          "file_type": ".csv"
        },
        {
          "document": "weather_data.csv",
          "bucket": "bucket_2",
          "file_type": ".csv"
        }
      ]
    }

This endpoint lists indexed source files. It does not return the complete text
of every chunk.


7. POST /query/stream
=====================

Purpose:
    Runs the same retrieval and answer-generation pipeline as /query, but
    returns newline-delimited JSON events while Qwen generates the answer.

Event types:
    status:
        Immediate progress message while retrieval starts.
    sources:
        The source citations selected for the question.
    token:
        One generated piece of answer text. The browser appends these pieces
        progressively to the response area.
    done:
        Indicates that answer generation is complete and includes the final
        answer and sources.
    error:
        Reports an Ollama or server error during streaming.

Example request:

    POST http://127.0.0.1:8000/query/stream

    {
      "question": "What is the swarm management advice?",
      "bucket": "bucket_1",
      "top_k": 3
    }

The response content type is application/x-ndjson. Each line is a separate
JSON event, for example:

    {"type": "status", "content": "Searching indexed context..."}
    {"type": "token", "content": "Swarm"}
    {"type": "token", "content": " management"}
    {"type": "done", "answer": "Swarm management...", "sources": []}

This endpoint improves perceived response time because the user sees text as
it is generated. It does not change the embedding or retrieval process.


8. POST /query
===============

Purpose:
    Runs the complete Retrieval-Augmented Generation pipeline and returns an
    answer grounded in the indexed documents.

Request body:

    {
      "question": "What is the swarm management advice?",
      "bucket": "bucket_1",
      "top_k": 5
    }

Fields:
    question:
        Natural-language question to ask.
    bucket:
        Optional bucket filter. If omitted or null, both buckets are searched.
    top_k:
        Number of final context chunks to use. Allowed range is 1 to 20.
        The default is 5.

Processing steps:
    1. Check that ChromaDB contains indexed chunks.
    2. Embed the question with BAAI/bge-base-en-v1.5.
    3. Search ChromaDB using cosine distance and the optional bucket filter.
    4. Retrieve top_k x 2 vector candidates.
    5. Rerank candidates with the local CrossEncoder model.
    6. Send the highest-ranked context and question to Ollama.
    7. Return the generated answer and source citations.

The configured Ollama model is currently qwen2.5:7b. The answer-generation
prompt instructs the model to stay within the retrieved context, answer
clearly, and cite the source filename and page where appropriate.

Example request:

    POST http://127.0.0.1:8000/query

    {
      "question": "What is the swarm management advice?",
      "bucket": "bucket_1",
      "top_k": 3
    }

Example response:

    {
      "question": "What is the swarm management advice?",
      "answer": "Swarm management requires consistent monitoring and small, regular adjustments. Beginners should start with a few reliable practices, keep records, and expand gradually. (Source: 28_urban_beekeeping_basics.pdf, page 2)",
      "bucket": "bucket_1",
      "sources": [
        {
          "document": "28_urban_beekeeping_basics.pdf",
          "page": "2",
          "bucket": "bucket_1",
          "file_type": ".pdf"
        }
      ]
    }

Possible errors:
    400:
        The vector store is empty. Run /ingest first.
    422:
        The request body failed validation, for example top_k is outside the
        range 1 to 20.
    503:
        Ollama is unavailable.
    500:
        Another RAG or server error occurred.


HOW THE ENDPOINTS WORK TOGETHER
===============================

Initial setup:

    POST /ingest
        -> parse files
        -> chunk text
        -> create embeddings
        -> store in ChromaDB

Question answering:

    POST /query
        -> embed question
        -> search similar chunks with ChromaDB
        -> rerank vector candidates with CrossEncoder
        -> ask Qwen
        -> return answer and citations

File replacement:

    POST /upload/{bucket}
        -> save uploaded file
        -> replace that file's old indexed chunks
        -> store its new chunks

Monitoring:

    GET /health
    GET /documents
    GET /documents/sources


IMPORTANT IMPLEMENTATION NOTE
=============================

GET /documents/chunks is implemented and returns stored chunks. The source
parameter is optional: when supplied, it filters to one exact document name;
when omitted, it returns a paginated view of chunks, optionally filtered by
bucket. DELETE /documents/{bucket}/{source} is not currently implemented.
